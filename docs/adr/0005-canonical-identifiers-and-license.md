# ADR-0005. Канонические идентификаторы схем, лицензия и способ потребления

## Статус

Accepted

## Контекст

Репозиторий `workout-contracts` является нормативным источником для нескольких
платформ: Desktop, Android и ESP32. Для долгосрочного использования необходимо
зафиксировать:

- лицензию на контракты, схемы, примеры и референсный инструментарий;
- канонические `$id` JSON Schema;
- способ подключения контрактов платформами;
- статус каталога `tools/`.

## Решение

### Лицензия

Репозиторий `workout-contracts` распространяется под лицензией Apache-2.0.

Выбор Apache-2.0 обоснован тем, что проект в перспективе включает Android и
ESP32, где патентная гранта лицензия является более безопасной, чем MIT.

Если в дальнейшем будет принято иное решение, замена на MIT возможна, но
потребует явного ADR и обновления `LICENSE`, `pyproject.toml`, `README.md`
и классификаторов пакета.

### Идентификаторы схем

Канонический базовый URL репозитория:

```text
https://github.com/krotOnLab/workout-contracts
```

Каждая схема должна использовать абсолютный `$id`, например:

```text
https://github.com/krotOnLab/workout-contracts/schema/workout.schema.json
https://github.com/krotOnLab/workout-contracts/schema/session-state.schema.json
https://github.com/krotOnLab/workout-contracts/schema/view-state.schema.json
https://github.com/krotOnLab/workout-contracts/schema/conformance-case.schema.json
```

### Способ потребления

Все платформы подключают `workout-contracts` через Git Submodule.

Публикация Python-пакета не является обязательной для потребления контрактов.
Каталог `tools/` рассматривается как референсный инструментарий для валидации,
нормализации и проверки согласованности каталогов.

Платформы не обязаны использовать `tools/` как библиотеку. Каждая платформа
реализует собственную валидацию и доменные модели согласно контрактам.

## Последствия

### Положительные

- Единая лицензия упрощает использование контрактов в закрытых и открытых
  платформенных проектах.
- Apache-2.0 снижает патентные риски для Android и embedded-платформ.
- Git Submodule даёт детерминированную фиксацию версии контрактов.
- `$id` схем становятся стабильными и привязанными к репозиторию.

### Отрицательные

- Необходимо дисциплинированно заменять placeholder `<org>` перед релизом.
- Git Submodule требует понимания у разработчиков платформ.
- `tools/` может ошибочно восприниматься как обязательная библиотека, поэтому
  его статус должен быть явно зафиксирован в README и ADR.
