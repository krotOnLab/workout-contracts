# Порядок изменения контрактов

1. Изменение начинается с issue с описанием сценария и граничного случая.
2. Если меняется семантика, добавляется ADR в `docs/adr/`.
3. Обновляются схема и каталоги, затем `docs/protocol.md`.
4. Добавляется или изменяется конформанс-вектор, покрывающий изменение.
5. Повышается `VERSION` по правилам `docs/versioning.md`, обновляется CHANGELOG.
6. CI должен проходить: согласованность каталогов, схемы, тесты, стабильность
   канонического экспорта.

Запрещено:
- менять вектор под поведение конкретной реализации;
- добавлять поле, влияющее на семантику этапов, в блок `runtime`;
- вводить событие, которое нельзя проверить вектором;
- вводить синонимы команд, в частности `CONFIRM` и `NEXT`.

Правила кодирования инструментария: Python 3.11+, docstring в стиле NumPy,
типизация обязательна, `ruff` без замечаний.

## Релизный чек-лист

Перед созданием тега `vX.Y.Z`:

1. Заменить `<org>` во всех `$id` схем на реальный URL репозитория.
2. Убедиться, что `LICENSE` содержит полный текст Apache-2.0.
3. Указать реального правообладателя в лицензии, если это требуется.
4. Проверить, что в `schema/` нет `example.org` и placeholder `<org>`.
5. Прогнать:

   ```bash
   wc-contracts check-catalogs
   pytest tools/tests -q
   ```

6. Обновить `CHANGELOG.md`.
7. Обновить `VERSION`.
8. Создать аннотированный тег:

   ```bash
   git tag -a v0.1.0 -m "workout-contracts v0.1.0"
   git push origin v0.1.0
   ```

9. В платформенных репозиториях обновить submodule до тега `v0.1.0`.
10. Прогнать платформенные конформанс-тесты.
